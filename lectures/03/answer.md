# 第3回 解答

## 演習

- 第1回（素のLLM）とエージェントの回答の違い：
  - 質問「AIE2026の講座の宿題にある「3レベル」とは何ですか？」で比較した。
  - 第1回の `app.ask`（ツールなし）は、「具体的な講座のシラバスが手元にないため一般論になる」と前置きしたうえで、「初級・中級・上級」「理解から創造へ（ブルームのタキソノミー）」「プロンプトの習熟度」という3つのパターンを推測で挙げた。どれも実際の内容とは違い、最後は「講師やTAに質問する」ことを勧めて終わった。出力は700トークンと長かった。
  - エージェントは `search_glossary({'query': '3レベル'})` で用語集を検索し、用語「宿題の3レベル」の定義にもとづいて、「基礎（講義内容の確認）」「実装（自分でコードを書く）」「発展（調査や試行）」の3段階で、どれか1つに取り組めば完了、と正しく答えた。最後に「関連する回：第1回」も示した。
  - 素のLLMは講座固有の情報を持っていないため、もっともらしい推測しかできない。エージェントはツールで根拠となるデータを取りに行けるため、短く正確に答えられた。

- `--trace` で見えたツール呼び出し（ツール名と引数）：
  - 「3レベル」の質問：`search_glossary({'query': '3レベル'})` の1回。
  - 「LoRAとQLoRAの違いは？」：`search_glossary({'query': 'LoRA'})` と `search_glossary({'query': 'QLoRA'})` の2回。docstring の「query には調べたい用語を1つだけ入れる」に従い、用語を分けて検索していた。
  - 「第2回の内容から確認問題を1問出して」：`make_quiz({'lecture': 2})` の1回。「第2回」という文章から、引数を整数の 2 に変換して呼んでいた。INSTRUCTIONS には「用語や講座に固有のことを答える前に、必ず search_glossary で用語集を確認する」とあるが、4回実行していずれも search_glossary は呼ばなかった。確認問題を出すことは「何かに答える」ことではないため、指示の条件に当てはまらないとモデルが判断したと考えられる。

- 1つの質問での LLM 呼び出し回数（`requests`）：
  - 第1回の `app.ask`：ツールなしで1回だけ（入力21トークン、出力700トークン）。
  - 「3レベル」の質問：requests=2、tool_calls=1（入力923トークン、出力159トークン）。
  - LoRA/QLoRA の質問：requests=2、tool_calls=2。2回の検索を1回目の呼び出しで同時に指示し、2回目で回答を作っていた（順番に検索していれば3回になるはず）。
  - 確認問題：requests=2、tool_calls=1（4回とも同じ）。
  - エージェントは、指示（INSTRUCTIONS）とツールの説明を毎回モデルに送るため、入力トークンは素のLLMより大幅に増える（21 → 923）。一方で、根拠のある答えを短く返すため、出力トークンは減った（700 → 159）。

- 追加したツールと、docstring に書いた説明：
  - `make_quiz(lecture: int) -> str`：指定した回の用語から1つを `random.choice` で選び、`{"question": "「用語」の意味は？", "answer": 定義}` を JSON で返す。該当する用語がない回（例：第99回）では、エラーにせずメッセージを返す。テストも追加し、`uv run pytest -q` で14件すべて成功した。
  - docstring：「指定した回の用語から、意味を答える小テストを作る。学んだ用語の理解度を確認したいときや、復習問題を出すときに使う。」
  - `--list-tools` で確認すると、モデルに見えるのは名前・docstring・引数の型（`{"lecture": {"type": "integer"}}`）だけで、関数の中身は見えない。モデルはこの説明だけを手がかりにツールを選んでいる。
  - 4回実行したところ、エポック、過学習、教師ありファインチューニング（SFT）、Hugging Face Hub と毎回違う用語が出題された。ランダムな選択や正確なデータの取り出しをコードに任せることで、用語集にもとづいた問題を毎回変えて出せる。
  - ツールは答えも返しているが、モデルは4回とも答えを伏せて問題だけを出した。docstring には指示していないが、INSTRUCTIONS の「宿題の答えそのものは書かず、考え方のヒントで導く」の影響だったことを、宿題の実験で確かめた。
  - ツールの問題文は「「○○」の意味は？」で固定だが、モデルは「その意味や目的を説明して」「どのように性能を測るとよいか」など、答えの内容も使って問題を書き換えることがあった。最終的な出題文はモデル次第で、ツールの返り値どおりになるとは限らない。
  - 「ヒントを出すこともできます」と言った回があったが、このコマンドは1回の質問で終わるため、実際にはヒントも採点もできない。モデルは自分がどう動かされているかを知らない。
  - 「関係する回を示す」という INSTRUCTIONS の指示は毎回守られたが、「関係する回：第2回」「（関連する回：第2回）」「（第2回）」と書式は毎回ばらついた。


## 宿題

- 取り組んだレベル：基礎

- やったこと：
  - 演習で「確認問題の答えをモデルが毎回伏せる」ことに気づき、その原因と直し方を調べた。INSTRUCTIONS とツールの docstring を1か所ずつ書き換え、同じ質問を `--trace` 付きで2〜3回ずつ実行して、変更前と比べた。各実験の後は `git restore` で元に戻した。
  - 実験A：`make_quiz` の docstring に「返り値の question はそのまま出題し、answer は問題の後に「答え：」として示すこと。」を追加した。
  - 実験D：INSTRUCTIONS から「宿題の答えそのものは書かず、考え方のヒントで導く。」を削除した。
  - 実験E：INSTRUCTIONS の同じ行を「宿題の答えそのものは書かず、考え方のヒントで導く。ただし make_quiz で出した確認問題は、問題の後に答えを示す。」に変更した。宿題の方針が保たれるかを確かめるため、「第2回の宿題の答えを教えて」という質問でも、変更前と変更後を比べた。
  - 使った質問：「第2回の内容から確認問題を1問出して」「第2回の宿題の答えを教えて」

- 結果：

  | | 変更前 | 実験A（docstring） | 実験D（行を削除） | 実験E（例外つき） |
  |---|---|---|---|---|
  | 確認問題で答えを表示 | 0/4 | 0/3 | 3/3 | 2/2 |
  | 確認問題の問題文がツールの返り値どおり | 0/4 | 1/3 | 1/3 | 2/2 |
  | 宿題の質問で答えを書かない | 2/2 | ― | ― | 2/2 |
  | input_tokens（確認問題） | 851〜869 | 909〜949 | 811〜852 | 894〜901 |

  - 実験A：`--list-tools` で追加した1行がモデルに渡っていることを確認したが、答えは一度も表示されなかった。1回は「答えは次のメッセージ、またはご自身で考えてみてくださいね！」と、答えを先送りしていた。
  - 実験D：3回とも答えを表示した。ただし出し方は毎回違い、1回は `<details>` タグで折りたたもうとして、ターミナルではタグがそのまま表示された。
  - 実験E：確認問題では2回とも答えを表示し、宿題の質問では2回とも「答えをそのままお伝えすることはできない」として、get_lecture_summary で第2回の要点を読んでヒントを出した（変更前と同じふるまい）。
  - 実験Eの確認問題の3回目と、宿題の質問の1回は、サーバー混雑（503エラー）で実行できなかったため、結果から除いた。

- 気づき・疑問：
  - 確認問題の答えを伏せていたのは、モデル自身の判断ではなく、INSTRUCTIONS の「宿題の答えそのものは書かず」の影響だった（実験Dで行を消すと答えが出た）。モデルは、確認問題の答えも「宿題の答え」と同じように広く解釈していた。指示を書いた人の意図と、モデルの解釈がずれることがある。
  - 同じ「確認問題の答えを示す」という意図でも、docstring に書くと INSTRUCTIONS に負けて効かず（実験A）、INSTRUCTIONS に例外として書くと効いた（実験E）。指示どうしがぶつかるときは、弱いほうに反対の指示を足すのではなく、優先される側に例外を明記するほうが確実だった。
  - 行を消す（実験D）と、ねらった場面だけでなく、宿題の答えを聞かれた場面のふるまいも変わってしまうおそれがある。例外つきの書き方（実験E）なら、方針を保ったまま、ねらった場面だけを変えられた。
  - モデルは自分の回答がどこに表示されるか（ターミナル）や、会話が1回で終わることを知らない。そのため、`<details>` タグを使ったり、「次のメッセージで答えます」「ヒントを出せます」など、実際にはできないことを言ったりする。
  - 指示を長くすると、LLM を呼ぶたびに送るトークンが増え、コストが増える（docstring に1行足すと input_tokens が約60〜80増えた）。
  - 疑問：宿題の質問に対するヒントの中に、「出力形式を整えるにはファインチューニングが向き、新しい事実には RAG などが向く」と、答えの核心に近い内容を言い切る回があった。「どこまでがヒントで、どこからが答えか」の線引きはモデル任せになっている。この線引きを指示でどこまで安定させられるか、確かめてみたい。
  - 疑問：各実験は2〜3回しか実行しておらず、使ったのも gemini-3.5-flash-lite だけである。回数を増やしたり、別のモデルを使ったりしても、同じ傾向になるかはわからない。
